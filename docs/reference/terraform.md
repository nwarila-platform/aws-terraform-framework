# Terraform Reference

The injected block below is regenerated by `make docs`; the `docs-diff` gate verifies it
during PRs. Do not edit by hand between the markers below.

## Interface-owned security-group rules

Rule resource keys use the declaring security-group name plus a content identity:
direction, lowercased protocol spelling, port range, destination kind, and
destination value. The readable values are sanitized and followed by a short
digest of the full identity. Rule descriptions do not affect identity.

The framework leaves AWS-owned rule-shape and duplicate-permission semantics to
AWS. The organizational exception is all-protocol scope: `-1`, its zero-padded
numeric equivalents, and `all` in any letter case require null ports because
EC2 ignores any supplied range and opens every port. Exact duplicate rules still
fail at plan time because their content-derived keys collide in Terraform's
object comprehension. Inserting or removing any other rule does not re-key
unrelated rules. Each rule's `Name` tag uses the same readable content identity
and digest as its resource key. The readable prefix is truncated as needed so
the digest remains within AWS's 256-character tag-value limit. The `Environment`
tag value is a closed, case-exact set - `dev`, `test`, or `prod` - so tag-based
inventory and cost queries never have to reconcile spelling or case variants.

## Interface-owned security groups

Each interface can declare exactly one framework-created group, named
`<hostname>-eni-<interface index>-sg`, and the framework attaches it only to
that interface. This is deliberate. Security groups shared across systems or
interfaces belong outside the framework and are referenced by ID through
`security_groups`.

`null` and `[]` have different meanings for `ingress` and `egress`. Paired
`null` values create no interface-owned group. Non-null lists create the group;
`[]` means the created group has no rules in that direction. The group's
description is set only when the group is created, and later description edits
are ignored to avoid replacement.

Network-interface identity is positional. Appending an interface is safe, but
inserting or reordering interfaces re-keys every later ENI and replaces its
interface-owned group and rules. A future stable-key option can be added without
changing existing position-derived identities.

Every ENI uses the default network card 0 while `device_index` continues to
match the interface's list position. This supports multiple ENIs on the common
single-network-card instance types. The framework does not currently expose
placement across multiple physical network cards.

The primary ENI uses `aws_instance.primary_network_interface`, preserving the
launch-time attachment that prevents EC2 from creating an unwanted default
interface. Interfaces at indexes 1 and above use position-keyed
`aws_network_interface_attachment` resources.

Existing deployments must import every already-attached secondary ENI before
applying this resource-address migration:

1. Upgrade to this configuration, but do not apply it yet.
2. Read each secondary ENI's attachment ID with
   `aws ec2 describe-network-interfaces`. Import it into
   `aws_network_interface_attachment.us_east_1["<hostname>-eni-<index>"]`, or
   the `us_east_1_refresh` twin when that system has `refresh = true`.
3. Run `terraform plan` and verify that it neither replaces an instance nor
   creates an attachment for an ENI that is already attached.

For example:

```console
aws ec2 describe-network-interfaces \
  --network-interface-ids eni-SECONDARY \
  --query 'NetworkInterfaces[0].Attachment.AttachmentId' \
  --output text
terraform -chdir=terraform import \
  'aws_network_interface_attachment.us_east_1["HOSTNAME-eni-1"]' \
  eni-attach-ATTACHMENT
```

## Standalone EBS volume state migration

Every standalone EBS entry now has a stable `resource_key` and `device_index`. To preserve the
old positional identities without moving state, set `resource_key` to the former zero-based list
index as a string and `device_index` to that index as a number. For example, the old
`HOSTNAME-ebs-0` entry becomes `{ resource_key = "0", device_index = 0, ... }`.

If you choose a descriptive resource key, move the existing volume and attachment addresses
before applying. The attachment destination is now always `aws_volume_attachment.us_east_1`:

For `refresh = true`, run the consolidation move below first, then these descriptive-key moves;
the attachment rename source exists only after consolidation. For `refresh = false`, the order
does not matter because attachments do not move between resources.

```console
terraform -chdir=terraform state mv \
  'aws_ebs_volume.us_east_1["HOSTNAME-ebs-0"]' \
  'aws_ebs_volume.us_east_1["HOSTNAME-ebs-data"]'
terraform -chdir=terraform state mv \
  'aws_volume_attachment.us_east_1["HOSTNAME-ebs-0"]' \
  'aws_volume_attachment.us_east_1["HOSTNAME-ebs-data"]'
```

This release consolidates refresh and stable attachments into that one resource. For every
affected state and every attachment on a `refresh = true` system, move its existing instance
before applying the new configuration:

```console
terraform -chdir=terraform state mv \
  'aws_volume_attachment.us_east_1_refresh["KEY"]' \
  'aws_volume_attachment.us_east_1["KEY"]'
```

Run `terraform -chdir=terraform plan` after the moves and verify that Terraform plans no EBS
volume detach or reattachment.

Standalone EBS volumes also now have one resource address regardless of their instance's
`refresh` setting. Existing deployments with refresh volumes must combine the old positional
key migration with the resource-name migration:

```console
terraform -chdir=terraform state list 'aws_ebs_volume.us_east_1_refresh'
terraform -chdir=terraform state mv \
  'aws_ebs_volume.us_east_1_refresh["HOSTNAME-ebs-0"]' \
  'aws_ebs_volume.us_east_1["HOSTNAME-ebs-data"]'
```

Repeat the applicable commands for every existing data volume, then run
`terraform -chdir=terraform plan` and verify that no standalone EBS volume or attachment is
destroyed or created.

## Secondary network-interface state migration

`aws_instance` no longer attaches interfaces with the deprecated inline
`network_interface` block. The index-zero interface is attached with
`primary_network_interface`, and every additional interface is now its own
`aws_network_interface_attachment` resource keyed exactly like the ENI it
attaches.

Existing deployments have those attachments recorded inside the instance rather
than as separate resources. Terraform will therefore plan to create an
attachment for an interface AWS has already attached, which fails. Import each
one first, using the ENI key and the attachment id AWS assigned:

```console
terraform -chdir=terraform import \
  'aws_network_interface_attachment.us_east_1["HOSTNAME-eni-1"]' \
  'eni-attach-EXAMPLE'
```

Use `aws_network_interface_attachment.us_east_1_refresh` for systems with
`refresh = true`. Interfaces at index zero need no import: they move from the
inline block to `primary_network_interface` in place.

## AWS security-group quotas

The framework does not impose rule, attachment, or group-count caps because AWS
quotas vary by account. The operative ceilings verified for the target account
are 60 ingress rules and 60 egress rules per security group (counted
separately), 5 security groups per network interface, and 2,500 security groups
per VPC.

These are adjustable quotas rather than hard framework limits. Operators MUST
check the target account and Region under **Amazon Virtual Private Cloud (Amazon
VPC)** in the AWS Service Quotas console, or with
`aws service-quotas list-service-quotas --service-code vpc`, before planning a
deployment near a ceiling.
